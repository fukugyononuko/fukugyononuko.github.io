# 0. 要件定義

## 0.1 背景と役割分担

運営者「副業のぬこ」の活動は、次の 2 つの場で役割を分ける。

| 場 | 役割 |
| --- | --- |
| **note** | 現時点で予定している収益化の主軸（有料記事、販売） |
| **このサイト** | 運営者に何ができ、どんなサービスを提供できるかを示し、依頼や note への導線になる |

収益化の主軸は今のところ note の予定だが、変わる可能性もある（他の販売サイトの追加、受託の比重が増えるなど）。どちらにしても、このサイト自体では決済をしない。役割を分けておくことで、収益化の場が変わってもこのサイトの中心的な役割は変わらず、変化は導線の切り替え（VOL-02）だけで済む。

### 出発点

運営者は副業を始めたばかりで、受託の実績も、売り物になっているプロダクトもまだない。そのため初期のサイトは、次の 2 つで能力を示す。

- **サービス（提供メニュー）**：「ホームページやモックを作れます」「データ解析をします」のような、依頼を受けられることの一覧
- **制作例**：受託の実績がなくても、個人で作ったものやサンプル（このサイト自体、モック、データ解析の例など）を載せる。ただし種類（受託 / 個人制作 / サンプル）を必ず明示し、サンプルを受託実績のように見せない

将来 note でテンプレートなどの商品を出す場合も、サービスと同じ枠で扱い、行き先を note にする（VOL-02）。

## 0.2 ビジネス要件（BR）

| ID | 要件 |
| --- | --- |
| BR-01 | 運営者に何ができるか（スキル・制作例）を訪問者に伝える |
| BR-02 | 運営者が提供できるサービスを示し、依頼につなげる |
| BR-03 | 収益化の場（現時点では note の予定）への導線を用意する。このサイトでは決済しない |
| BR-04 | 維持費をかけず、運営者 1 人で簡単に更新・公開できる |
| BR-05 | 問い合わせ手段や取引の場など、将来の変化に、サイト全体を作り直さずに対応できる |
| BR-06 | 運営者の個人情報（本名・住所・私用メールなど）を公開しない |
| BR-07 | サイトが改ざんや悪用をされず、訪問者と運営者を危険にさらさない |

## 0.5 コアユースケース（UC）

The Method に従い、ユースケースは少数の本質的なものだけに絞る。画面や機能ごとに 1 つずつ作ることはしない。

| ID | ユースケース | アクター | 実現する FR |
| --- | --- | --- | --- |
| UC-01 | 運営者の能力を知る | 訪問者 | FR-01, FR-02, FR-03, FR-09, FR-10 |
| UC-02 | サービスを検討する | 訪問者 | FR-04, FR-05, FR-06, FR-07, FR-09 |
| UC-03 | 依頼について問い合わせる | 訪問者 | FR-07, FR-08 |
| UC-04 | 外部の場（note など）へ移る | 訪問者 | FR-07, FR-10 |
| UC-05 | コンテンツを更新して公開する | 運営者 | FR-13, FR-14 |
| UC-06 | ニュースを読み、広める | 訪問者 | FR-11, FR-15, FR-16, FR-17 |

FR-12（404）はユースケースではない。Client だけで完結する付随機能として扱う。

### UC-01 運営者の能力を知る
1. 訪問者がトップページを開く。
2. 注目のスキル・制作例を見る。
3. About ページで、プロフィール、スキルの全体、制作例の一覧を見る。
4. （任意）外部チャネルへのリンクから note・X・GitHub に移る（UC-04 へ）。

### UC-02 サービスを検討する
1. 訪問者がトップまたはナビゲーションからサービス一覧を開く。
2. 一覧から 1 つを選び、詳細を開く。
3. 価格（価格表示ポリシーに従った表示）、提供内容、納期の目安を確認する。
4. 行動喚起に従って、UC-03（問い合わせ）か UC-04（外部の場）に進む。

### UC-03 依頼について問い合わせる
1. 訪問者が問い合わせページを開く。サービスの詳細から来た場合は、そのサービスを指定した状態で開く。
2. その時点で使っている問い合わせ手段（フォーム、外部サービス、DM など）で連絡する。

### UC-04 外部の場へ移る
1. 訪問者が、共通フッター、サービスの行動喚起、または記事のページのフォローのリンクから外部チャネルを選ぶ。
2. 新しいタブで外部の場が開く。

### UC-05 コンテンツを更新して公開する
1. 運営者がコンテンツファイル（Markdown / YAML。ニュースの記事を含む）を編集する。
2. `main` に push する。
3. CI がビルド、スキーマ検証、依存規則の検査を行う。
4. すべて成功すれば GitHub Pages に公開される。失敗すれば公開されず、運営者に違反箇所が示される。

### UC-06 ニュースを読み、広める
1. 訪問者が、トップの「最新のニュース」、ナビゲーションのニュース一覧、または RSS リーダーから記事を開く。
2. 分類・公開日・見出し・画像・本文を読む。
3. （任意）共有ボタンで記事を SNS に共有するか、リンクをコピーする。共有先は新しいタブで開く。
4. （任意）フォローのリンクから外部チャネルに移る（UC-04 へ）か、関連記事を開く（2 へ）。

ニュースの記事は運営者がこのサイトに書く。参考にしたのは、ユーザーが示した資料（NASA のニュースリリースのページ）の構成で、色と形はこのサイトのデザイン（02a §2a.7）のままにする。

## 0.6 未決事項（OPEN）

どの未決事項も、影響が 1 つの変動性（VOL）の中に閉じるように設計してある。そのため、未決のままでも設計と実装を進められる。

| ID | 内容 | 影響する変動性 | 決める期限 |
| --- | --- | --- | --- |
| OPEN-01 | 問い合わせ手段 → **解決済み**：Formspree（form-post、無料プラン）。受信は副業のぬこ用のアドレス | VOL-01 | フェーズ 4 |
| OPEN-02 | サービスメニュー → **解決済み**：「ホームページ・モックの制作」「データ解析」の 2 つ | VOL-05（データ） | フェーズ 4 |
| OPEN-03 | 価格表示 → **解決済み**：当面は全サービス「お見積もり」（`price.kind: quote`）。相場がつかめたら見直す | VOL-03 | フェーズ 4 |
| OPEN-04 | 掲載する外部チャネル → **解決済み**：note（https://note.com/fukugyo_no_nuko ）と GitHub | VOL-07 | フェーズ 4 |
| OPEN-05 | デザインの方向性 → **解決済み**：アイコンの写真に合わせた「木漏れ日の砂浜」（02a §2a.7） | VOL-10 | フェーズ 2 |
| OPEN-06 | アクセス解析 → **解決済み**：当面は入れない（外部スクリプトなし。入れるときは VOL-09 で設定だけ変える） | VOL-09 | フェーズ 5 |
| OPEN-07 | 最初に載せる制作例 → **解決済み**：このサイト（個人制作）と、消費者物価指数の分析（サンプル、https://github.com/fukugyononuko/cpi-analysis ） | VOL-05（データ） | フェーズ 4 |

## 0.7 スコープ外

- 決済、会員登録、ログイン（収益化は外部の場で行う。現時点では note の予定。BR-03）
- サーバーで動く処理（GitHub Pages は静的ホスティングのため）
- 独自ドメイン（ただし VOL-08 として移行できるようにはしておく）
- 多言語化（01 §1.3 で、変動性として扱わないと判断した）
