## RCA

### P-01：補った前提を事実として書いた

- なぜ 1：設計書を簡易版にした。プロダクトがある前提で書いた。note で収益化すると断定した。
- なぜ 2：ユーザーの短い発言（「ホームページ」「どのようなプロダクトなら提供できるか」「収益化側面は note」）から、Claude が足りない部分を補い、その結果を要件として書いた。
- なぜ 3：補った部分を「確認すべき仮定」として、事実と分けて示していなかった。
- なぜ 4：質問を減らして早く進めることを優先し、フェーズの始めに前提を一覧にして確認する手順を持っていなかった。
- **根本原因**：Claude が補った前提を、仮定として明示して確認する手順がない。
- **再発防止策**：T-01（フェーズの始めに前提と仮定を一覧にして確認する。手順書とメモリーに反映）。

### P-02：積んだ PR が閉じられた

- なぜ 1：#3 を `--delete-branch` 付きでマージしたため、#4 のベースのブランチが消え、GitHub が #4 を閉じた。
- なぜ 2：#3 のマージを待たずに次のフェーズを進めるため、#4 を #3 のブランチの上に積んだ。
- なぜ 3：マージ待ちの PR があるときの進め方（待つか、積むか）を決めておらず、積んだ場合の GitHub の挙動も確かめていなかった。
- **根本原因**：マージ待ちの PR があるときの進め方の決まりがない。
- **再発防止策**：T-02（PR は常に `main` から作る。前の PR がマージされるまで次の PR は作らない）。
- 未検証：#4 で CI が自動で動かなかった原因は確かめていない（推定：ベースが `main` 以外の PR だったこと）。T-02 によりこの状況は起きなくなるので、調査はしない。

### P-03：依存の制約を設定に残さなかった

- なぜ 1：Dependabot が TypeScript 7 への更新 PR を作り、`npm ci` が依存関係の衝突で失敗した。
- なぜ 2：TypeScript 6 を選んだ理由（`@astrojs/check` の対応範囲）を、どこにも残さなかった。
- なぜ 3：「最新を使わない」という判断を、自動化の設定に反映する手順がなかった。
- **根本原因**：依存のバージョン制約の判断を、Dependabot の設定に残す手順がない。
- **再発防止策**：T-03（依存を最新以外に固定したら、同じ PR で Dependabot の ignore と理由を書く）。

### P-04：詳細設計の穴

- なぜ 1：契約の型に、必要な項目や責務が欠けていた。
- なぜ 2：コールチェーンでは「どの構成要素がどの順に呼ばれるか」は示したが、View の各項目のデータがどこから来るかを一つずつたどっていなかった。
- なぜ 3：使うフレームワーク（Astro）の制約を、詳細設計の段階で試して確かめていなかった（Markdown の描画、`.astro` ファイルの依存解析など）。
- **根本原因**：詳細設計に「データの出所」と「フレームワークの制約」を検証する手順がない。
- **再発防止策**：T-04（実装を始める前に、各 View の項目のデータの出所を利用規則に照らして確かめる。フレームワークに依存する前提は、小さく試して確かめる）。
