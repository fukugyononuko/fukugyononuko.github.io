## RCA

### P-01：参考のページのレイアウトの取り違え
- なぜ 1：レイアウトの案 A を「NASA に近い縦 1 列」と説明した。
- なぜ 2：参考のページの構成を、取得した HTML の文章の順から読み取った。HTML では左の列が見出しより後ろに書かれていて、1 列に見えた。
- なぜ 3：参考のページを描画して見なかった。スクリーンショットを撮る道具（Playwright）は手元にあったが、使うのは自分の作ったページだけだった。
- なぜ 4：見た目の案を出す手順（決まり 9）は「案を並べて選んでもらう」ことだけを決めていて、案の元になる参考の見た目をどう確かめるかを決めていない。
- 根本原因：参考にする見た目を、描画した画面ではなく HTML の文章から読み取る手順になっていて、参考の画面を描画して確かめる手順がない。
- 再発防止策：開発の決まり 21（参考の見た目は、PC 幅とスマホ幅で描画したスクリーンショットで確かめ、案に添えて同じところと違うところを書く。完成の確認も、公開する実際のコンテンツで参考と並べて行う）。プログラムの `CLAUDE.md` にも同じ趣旨を書く。P-03 もこの策で防ぐ。

### P-02：溜まっていた PR の見落とし
- なぜ 1：#36 だけをマージしようとした。
- なぜ 2：開いている PR の一覧を、セッションの始めにもマージの前にも見なかった。
- なぜ 3：Dependabot の PR は issue にも vault のノートにも載らず、作業の流れ（issue → PR）の外で作られるので、目に入る仕組みがない。
- 根本原因：セッションの始めや PR をマージする前に、開いている PR（Dependabot を含む）と失敗している CI を一覧する手順がない。
- 再発防止策：プログラムの `CLAUDE.md` に手順を書く（毎回読み込まれるため）。開発の決まり 22 にも書く。

### P-04：条件の合わない数値の採用
- なぜ 1：音読の速さ（IReST）を使った。
- なぜ 2：日本語の値が言語ごとの表にある出典を先に見つけ、そのまま採った。
- なぜ 3：測定の条件（音読か黙読か）を確かめたのは、値を決めて設計を書いたあとだった。
- 根本原因：外部の研究の値を定数に使うときに、測定の条件が使う場面と合うかを、決める前に確かめる手順がない。
- 再発防止策：開発の決まり 23（測定の条件を使う場面と照らしてから値を決める。合わなければ合う出典を探し、見つからなければ決める前にユーザーに確かめる）。

### P-05：結合テストの Engine への依存
- なぜ 1：速さを変えたら TC-I02 が失敗した。
- なぜ 2：TC-I02 が本物の ReadingTimeEngine を使い、「358 字なら 2 分」という規則に依存した期待値を持っていた。
- 根本原因：Manager の結合テストで、Engine の規則に依存する期待値を持たせない、という決まりがない（変動性の閉じ込めをテストの側で守る手順がない）。
- 再発防止策：開発の決まり 24（Manager の結合テストでは、変動性を閉じ込めた Engine を、規則を知らない偽物に差し替える）。
